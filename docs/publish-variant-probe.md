# DeskBox 发布参数对冷启动前段耗时的实测报告

> 测量对象：`src/DeskBox`（工作树，含 Lead 的 `StartupTrace` 启动埋点；HEAD 之外的工作树改动）。
> 测量环境：Windows 11 Pro 26300 / Ryzen 9 9950X（16C32T）/ 93.4GB RAM / NVMe SSD；.NET SDK 8.0.421（`global.json` 固定，临时副本内）；win-x64 self-contained。
> 测量方式：全部在 `%TEMP%\deskbox-publish-probe\` 的源码副本里构建、运行；未修改仓库 `src/`、`dist/`，未启动/结束任何正式 `dist\DeskBox.exe` 进程。
> 测量时间：2026-10-18 11:12–11:21（后台有游戏客户端等常驻程序，见 §7 噪声说明）。
> 结论先行：**发布默认保持 V0（现状：单文件 + 压缩，不开 ReadyToRun）**；若以启动速度为第一目标，选 V1（单文件不压缩）。差异不是噪声，是明确的「0.17 秒 vs 96MB」取舍。

---

## 1. 结论摘要（TL;DR）

1. **推荐发布参数：V0（现状）**——`self-contained + PublishSingleFile + IncludeNativeLibrariesForSelfExtract + EnableCompressionInSingleFile`，不开 ReadyToRun。
   - 体积最小：**70.1MB** 单文件；暖态「进程入口」**349ms**（6 个暖样本中位数，下同）。
   - 压缩的代价是每次启动多 **~176ms**（进程入口 349 vs 不压缩 V1 的 173.5ms，墙钟 475 vs 276ms），换来体积从 166.2MB 降到 70.1MB（**2.37×**）。开机自启每次都要付这 176ms，但下载/磁盘占用只付一次 96MB；按本项目「绿色单文件发布」的形态，推荐保留压缩。
2. **若「启动速度」优先：选 V1（单文件不压缩）**。单文件形态仍成立，暖态进程入口 **173.5ms（约 -50%）**、墙钟 **276ms（约 -42%）**；代价是 **166.2MB（2.37×）**。这是唯一值得考虑的速度向替代方案。
3. **不要开 ReadyToRun**：
   - V2（压缩 + R2R）：暖态进程入口 **589ms**，比 V0 还慢 **+240ms**、比 V3 慢 **+418ms**，体积反而 +17MB —— 全面劣化（R2R 让程序集变大、更难压缩，每次启动解压成本盖过 JIT 收益）。
   - V3（不压缩 + R2R）：暖态进程入口 **171.5ms**，与 V1 的 173.5ms 差异在噪声内（**无收益**），体积 +61MB 到 227.3MB。→ 本应用（WPF、自包含）开 R2R 不值得。
4. **目录发布（V4）最快但不可发布**：暖态进程入口 **152.5ms** / 墙钟 **252.5ms**，比 V3 只快 **~19ms / ~11ms**（接近噪声边缘），但产物是 **270 个文件、172.3MB** 的目录，放弃「绿色单文件」。只适合本地调试/增量更新形态。
5. **首次解压成本很小，不是瓶颈**：压缩/不压缩单文件首次启动都要把 5 个 native DLL（7.8MB）解压到 `%TEMP%\.net\DeskBox\<bundle-id>\`；实测首启只比稳态多 **+70~78ms**（压缩，需解压）/**+29~34ms**（不压缩，纯拷贝）。审计文档里「解压 0.5–2s」的推测不成立。
6. **噪声**：同一变体 6 个暖样本「进程入口」极差 9–46ms，跨会话中位数漂移 3–23ms；压缩带来的 ~176ms、R2R+压缩带来的 +240ms 远超噪声。V3↔V1（-2ms）在噪声内；V4↔V3（-19ms）接近噪声边缘，不足以据此改发布形态。

**一句话决策表**

| 目标 | 选 | 暖态进程入口（中位数） | 单文件体积 |
|---|---|---|---|
| 发布默认 / 体积优先（推荐） | **V0 压缩单文件** | 349ms | **70.1MB** |
| 启动前段优先 | V1 不压缩单文件 | 173.5ms | 166.2MB |
| 不推荐 | V2 压缩+R2R | 589ms | 87.1MB |
| 不推荐 | V3 不压缩+R2R | 171.5ms（≈V1，噪声内） | 227.3MB |
| 不推荐（形态不符） | V4 目录发布 | 152.5ms | 172.3MB（270 文件） |

## 2. 测量方法

### 2.1 构建

- 把 `src\DeskBox` 复制到 `%TEMP%\deskbox-publish-probe\src\DeskBox`（排除 `bin`/`obj`），副本内放 `global.json` 固定 SDK 8.0.421（仓库本身未动）。
- 按任务给定的 5 组参数串行 `dotnet publish`（各自独立 `-o` 输出目录），命令模板：

```powershell
# 通用前缀
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true `  # V4 不带 PublishSingleFile
  -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=<true|false> `
  -p:PublishReadyToRun=<true|false> -o <变体目录>
```

| 变体 | 压缩 | R2R | 单文件 | 说明 |
|---|---|---|---|---|
| V0 | ✅ | ❌ | ✅ | 现状基线（= README 发布命令） |
| V1 | ❌ | ❌ | ✅ | 单文件不压缩 |
| V2 | ✅ | ✅ | ✅ | 单文件压缩 + ReadyToRun |
| V3 | ❌ | ✅ | ✅ | 单文件不压缩 + ReadyToRun |
| V4 | — | ❌ | ❌ | 目录发布（自包含、非单文件） |

- 构建耗时：V0（含首次 restore+编译）16.8s；V1 1.4s（增量重打 bundle）；V2 48.9s（首次 Crossgen2 全量 R2R）；V3 1.7s、V4 1.9s（复用编译/R2R 产物）。全部 exit=0。

### 2.2 运行与取数

- 每个变体每轮会话用 `DeskBox.exe --desktop-icons-probe` 实跑 4 次：该参数在 `App.OnStartup` 里、单实例锁之前就读桌面图标并 `Shutdown`，不显示窗口、不读写用户配置（实测变体目录里只出现 `deskbox.log`，没有 `config.json`）。
- 墙钟 = 包 `Start-Process -Wait` 的 `Stopwatch`；两轮会话共 40 次运行（主表 20 次 + 复核 20 次）全部 exit code 0。
- 启动毫秒数从该变体目录 `deskbox.log`（追加写）里按前缀取**最后一次**出现的三行，正则抽「自进程启动 Xms」：
  - `[启动] 模块初始化（托管入口）`（.NET 宿主/单文件 bundle 加载完成、进入托管入口）
  - `[启动] App 构造（WPF 入口）`（WPF `Application` 构造完成）
  - `[启动] 进程入口`（`OnStartup` 开始）
- **「第 1 次」与「第 2~4 次」的区分**：每变体用独立的 `DOTNET_BUNDLE_EXTRACT_BASE_DIR`，并在第 1 轮前**清空**该目录 ⇒ 第 1 次一定是「解压缓存缺失」的首启状态；第 2~4 次复用解压缓存，是「重启后 TEMP 缓存还在」的稳态。
  - 发现：V0/V1 的 bundle id 相同（压缩参数不改变托管程序集内容），V2/V3 相同（R2R 改变了程序集）——若共用一个 `%TEMP%\.net`，V1 会白嫖 V0 的解压目录、V3 会白嫖 V2 的，导致首启数据失真。上表用独立目录规避。
- 计两轮独立会话（各 4 轮跑法，会话 A 顺序执行、会话 B 轮转执行以摊平机器负载漂移），共 8 次/变体；正文主表给会话 B 的 4 次原始值，汇总用两会话 6 个暖样本的中位数。

### 2.3 指标含义（按日志行号/源码）

| 指标 | 含义 | 覆盖的启动成本 |
|---|---|---|
| 模块初始化 | 托管入口（`[ModuleInitializer]`） | 进程创建、apphost/hostfxr、运行时初始化、单文件 bundle 打开、native 解压（首启）、`StartupTrace` 静态初始化 |
| App 构造 | WPF `Application` 构造函数结束 | 加载 `PresentationFramework/Core/WindowsBase` 等、WPF 全局初始化 |
| 进程入口 | `App.OnStartup` 开头 | `base.OnStartup`、`App.xaml` InitializeComponent（资源/主题字典）等 |
| 墙钟 | Start-Process→进程退出 | 上述 + `--desktop-icons-probe` 读桌面图标、`Shutdown()`、进程退出（约 85–130ms，各变体相近） |

> 本测量路径不加载主窗口/盒子/玻璃引擎，因此**只覆盖「盒子上屏之前」的前段**；ReadyToRun 对首盒 XAML/业务代码 JIT 的可能收益不在本报告结论范围内（需 Lead 的真启动埋点验证）。
> `自进程启动` = `DateTime.Now - Process.StartTime`，分辨率约 1–16ms，对本文 30ms 级以上差异足够。

## 5. 解读与取舍

1. **压缩 vs 不压缩（V0 ↔ V1）是唯一值得做的取舍**：稳态度量下，压缩让每次启动多付 **~176ms**（进程入口）/ **~199ms**（墙钟），体积省 **96.1MB（−57.7%）**。差值是噪声（9–46ms 极差）的 4–8 倍，**真实存在**。
2. **ReadyToRun 在本应用前段没有收益，与压缩组合还是负收益**：V3 ≈ V1（-2ms，噪声内），V2 比 V0 慢 240ms。原因是本应用前段的耗时大头是「从 bundle 加载/解压程序集」，R2R 只是省 JIT；框架程序集已经高度优化，JIT 不是前段瓶颈，R2R 增大体积反而放大解压成本。
3. **目录发布（V4）只快 ~19ms**：省掉单文件 bundle 的加载/映射，但「多文件冷读 270 个文件」在真实冷盘下不占优；本机稳态也只有 19ms 优势，且彻底放弃单文件形态，不划算。
4. **首启解压不构成问题**：7.83MB/5 个 native DLL，压缩变体一次性多 ~78ms、不压缩变体多 ~34ms（纯拷贝）。真正的一次性成本是「这台机器上第一次执行这个新 exe」（Defender 扫描 + 冷盘读，见 §7），换版本后第一次启动单文件变体约多 0.8–1.4s（目录发布约 0.3s），和压缩参数无关。（注：`docs/boot-timing-audit.md` §2.3 记的解压缓存「30 个文件/49MB」与实测不符——`%TEMP%\.net\DeskBox` 下现存所有 DeskBox 解压目录（含 10-15 构建的 `8tjAWo_7IuJZ`）都是 5 个文件/7.83MB，含 `D3DCompiler_47_cor3`、`wpfgfx_cor3`、`PresentationNative_cor3`、`PenImc_cor3`、`vcruntime140_cor3`，原因应是其余 native 库已 prelink 进 host；以实测为准。）
5. **对开机冷启动的提示**：本报告测的是「解压缓存已存在 + OS 文件缓存热」的稳态。真实开机那一刻文件缓存是冷的：V0 的 70MB 冷读 vs V1 的 166MB 冷读会部分抵消 V1 的 176ms 优势；本机 NVMe 很高，抵消有限，但**无法在不重启/不清空系统缓存的情况下直接测**。因此若以「开机自启那一刻」为第一目标，保守选 V0（体积小=冷读少、已有 6 次实测基线）；若以「用户再次启动/程序内重启」为主，V1 更快。两者都远优于开 R2R。

## 6. 推荐

- **发布默认：V0（保持现状）** —— 单文件 + 压缩，不开 ReadyToRun。70.1MB、暖态前段 349ms/475ms；以每次启动 ~0.18s 换 96MB 体积，对绿色单文件发行版是本项目的最优平衡点。
- **可切换项：若明确以启动前段为第一优先级**（可接受 166.2MB 下载体积），改 V1（去掉 `-p:EnableCompressionInSingleFile=true` 或设为 false），前段可减半（-176ms 进程入口 / -199ms 墙钟），构建参数只改一个，随时可切。
- **明确不采用**：
  - V2 / V3（ReadyToRun）：前段无收益或负收益、体积大增；若未来要验证 R2R 对「首盒上屏」后段的收益，应配合关闭压缩（V3）单独测，不能与压缩同开。
  - V4（目录发布）：仅 19ms 优势、270 文件，违背绿色单文件定位。
- **README 发布命令保持现状即可**，无需因本次测量改动；若采用 V1 需在 README/发布脚本改压缩参数并说明体积变化。

## 7. 噪声、局限与可信度

- **噪声来源**：测量期间机器上有常驻游戏客户端（DeltaForceClient 等）和 IDE/Agent 进程；两次会话的绝对值有 10–40ms 级漂移（例如 V1 暖态进程入口在会话 A 为 176–209ms、会话 B 为 163–171ms）。故汇总用两会话 6 个暖样本的中位数，并保留范围。
- **超过噪声的差异（可下结论）**：压缩代价 +176ms；R2R+压缩 +240ms；V0/V1 与 V2 之间的体积与启动差。
- **在噪声内/边缘（不下结论）**：V3 vs V1（-2ms）；V4 vs V3（-19ms，接近噪声）；V3 与 V1 的墙钟差（-12ms）。
- **局限**：① `--desktop-icons-probe` 在单实例锁之前退出，只覆盖前段，不含盒子/玻璃/托盘等后段；**不能据此否定 R2R 对后段的可能性**。② OS 文件缓存无法在不重启的前提下清空，「真·开机冷启动」的冷盘读取成本未直接测量，结论中的冷读影响为基于首启与稳态数据的推断。③ 首启样本每个变体只有 2 个，且 exe 在本机已执行过，首次执行的 Defender/冷盘一次性成本只能参考 §7 附注。④ 构建用 SDK 8.0.421、win-x64、同一台机器，其他机器绝对值会不同，但参数间相对关系（压缩慢、R2R 无益）预计可迁移。

**附注（一次性首次执行成本，单样本、仅供参考）**：最早一轮测量中，每个 exe 在本机第一次执行时的墙钟为 V0 1836ms / V1 1152ms / V2 1472ms / V3 1259ms / V4 514ms（对应暖态 446/259/667/248/233ms）。这部分是新建 exe 被 Defender 扫描 + 冷盘读取的一次性成本（单样本、且受执行顺序影响），不代表每次启动；但可说明「换版本后第一次启动」单文件变体约多花 0.8–1.4s、目录发布约 0.3s。

  $env:DOTNET_BUNDLE_EXTRACT_BASE_DIR = "$env:TEMP\deskbox-publish-probe\extract-base4\V0"
